# 2026-11-17

## Tests that build both sides from one assumption hide integration bugs

- **Root cause**: Stage 13's merge tests made the "Semgrep" finding by
  copying the AI finding and changing only the title's capitalization, and
  every scanner test mocked `subprocess.run` with hand-written JSON. Real
  Semgrep titles are rule IDs and Bandit's are "B105: ...", with different
  severities and CWEs, so in practice nothing merged (8 problems became 24
  findings), and the tools weren't even installed. All tests passed.
- **Rule**: When code combines output from external tools, record the
  tools' real output once (with the exact command line) and test against
  those recordings, plus a small test that runs the real tool and is
  required in CI. Match on something the sources actually share, and add
  "must not merge" cases.
- **Signal**: A test fixture created by copying the other side's input, or
  an integration whose only tests mock the process call.

## A CLI tool's dependencies can conflict with the app's

- **Root cause**: `semgrep==1.184.0` pins `click~=8.4.2`, which pip can't
  resolve with the backend's `uvicorn[standard]==0.30.6`, so it couldn't go
  in `requirements.txt`. Bandit could.
- **Rule**: Run command-line tools the app only calls as subprocesses from
  their own environment (pipx or a separate venv), pinned in their own file,
  and install them separately in CI. Check `pip install` of the whole set
  in a clean container before adding a tool to requirements.
- **Signal**: Adding a large CLI tool (scanner, linter, formatter) to the
  app's requirements file.

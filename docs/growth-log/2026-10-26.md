# 2026-10-26

## Hard-coded value lists copied between components drift apart

- **Root cause**: The History filter re-typed its own language list
  (`c++`, `typescript`) instead of using the values the submit form actually
  stores (`cpp`, `c`, `other`). The backend compared exactly, so "C++" always
  returned 0 results and C/Other could not be filtered. The backend test
  passed because it used correct values; the bug lived only in the frontend
  copy.
- **Rule**: Any list of values that gets stored (languages, statuses,
  severities, categories) has one exported source that both the writer and
  every reader import. Labels are a separate map keyed by the stored value.
- **Signal**: A `<select>` or `<option>` list for a field that another
  component also writes, or a filter test that only exercises
  backend-generated values.

## User search terms passed straight into LIKE patterns

- **Root cause**: `f"%{q}%"` passed to `ilike` makes `%` and `_` in user
  input act as wildcards (`q=%` matched every review). It's parameterized, so
  not SQL injection, but the results are wrong.
- **Rule**: Use SQLAlchemy `col.icontains(term, autoescape=True)` (or
  `contains`/`startswith` with `autoescape=True`) instead of building LIKE
  patterns by hand.
- **Signal**: `ilike(f"%{...}%")` or `like(f"%{...}%")` anywhere in a route.

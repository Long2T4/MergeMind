# 2026-11-13

## "Get or create" on first sign-in races with the app's own parallel requests

- **Root cause**: After sign-in the browser sends several API calls at once.
  Each looked up the user by auth UUID, found nothing, then checked the
  email before creating the row. When another request committed the row in
  between, the email check fired and returned "requires administrator
  linking" (6 of 120 first requests in testing). Single-request tests
  passed; only parallel requests showed it.
- **Rule**: Any lookup-then-insert must handle the row appearing between the
  two steps: re-check by the same unique key (here the verified auth UUID),
  not a weaker one like email, and catch the unique-constraint error on
  insert. Test it with truly parallel requests on PostgreSQL, not only
  sequentially.
- **Signal**: A "get or create" on the first request after login, or any
  first-use path the frontend can hit from several components at once.

## Access rules hidden in a global query hook miss work outside requests

- **Root cause**: Stage 12 first filtered every query through a global ORM
  hook fed by the current request's user. Background pull request reviews
  run without a request, so they broke, and a route that bypassed the hook
  would have no protection at all. Nothing in the route code showed which
  data it was allowed to see.
- **Rule**: Check ownership explicitly in each route (a shared helper such as
  `owned_project_ids(user_id)` is fine), and keep background work free of
  request context. Prove it with a two-user test against every route, and
  list the app's routes to confirm each depends on the signed-in user.
- **Signal**: Security that depends on a context variable or middleware
  "magic" rather than a visible filter, or a new route (like a trends or
  stats endpoint) added without `get_current_user`.
